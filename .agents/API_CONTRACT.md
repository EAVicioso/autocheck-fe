# Consumo del contrato HTTP

El [contrato original](../API_CONTRACT.md) fija rutas, wire, autenticación y los códigos de error. El [handoff de dominio](../BACKEND_CONTEXT_TRANSFER.md) aporta flujos e invariantes. [El módulo generado](../src/shared/api/contract.generated.ts) contiene las 57 operaciones de negocio. Salud y documentación están en la fuente. El webhook tiene tipos para fines de trazabilidad y queda excluido del cliente general.

1. Actualiza la fuente solo desde un contrato confirmado de AutoCheck. Revisa los cambios de estado, parámetros y tipos de todas las fichas afectadas.
2. Ejecuta `npm run contract:generate` tras actualizar el Markdown y `npm run contract:check` para comprobar que la salida se reproduce. El generador falla ante un recuento distinto de 57 o una ficha que no puede interpretar.
3. Usa `operations` y `Operations[Método Ruta]` para auth, bindings, respuestas y códigos específicos por estado. Mantén los transversalmente documentados en `Problem`. `Version` tiene proyección exacta a `bigint` si el Int64 excede el rango seguro de JS. El cliente conserva el número JSON del wire. Toda lectura o serialización fuera del cliente debe mantener esa precisión.

- Separa challenge JWT 401, expiración o invalidación de aplicación 401, credenciales 401, 403, 409, 429 y fallos de red. El BFF elimina estado local en invalidación definitiva. GET y refresh no registran actividad. Respeta `Retry-After` y propaga la señal de cancelación.
- Lee `application/problem+json` conservando códigos, traceId y rutas de error. `formErrorPath` traduce rutas como `Defectos[0].Descripcion` a `defectos.0.descripcion`. Valida los nombres contra los campos del formulario. Conserva errores generales y los desconocidos como feedback de formulario.
- Para una mutación con `Idempotency-Key`, conserva la misma clave y el mismo cuerpo ante un resultado incierto. `client.prepare` fija ruta, query, encabezados y bytes del cuerpo para el siguiente intento dentro del flujo. Genera clave nueva al cambiar los datos. El cliente permite una repetición por challenge de transporte solo para GET o una operación con idempotencia documentada. Tras un POST de estado asíncrono usa el GET correspondiente para reconciliar.
- Los cursores son opacos. Conserva filtros, orden y dirección, y omite `pagina` o usa 1 en el siguiente cursor. `siguienteCursor: null` indica fin. `Items<T>` tiene forma distinta de una página. El wire mantiene fechas locales y UTC según la ficha.
- Usa `Location`, `Retry-After` y `Content-Disposition` en la frontera de servidor. Si no están disponibles por CORS o en la respuesta, usa el campo de cuerpo documentado cuando sea aplicable. `204` carece de cuerpo. Maneja el PDF como bytes de `application/pdf` del backend con Bearer y nombre en Content-Disposition cuando esté presente.
- La consulta pública pasa el ID y hash a la ruta anónima. Presenta los cuatro campos públicos y distingue 200, 404 y 409. Los QR emitidos abren el JSON actual de la API. Enlazar nuevos QR a `/verificar/[id]` depende del backend o del enrutamiento del despliegue.
- La asistencia tiene su propio esquema estricto de tres claves. El límite de 3 s cubre trabajo local, red y lectura del cuerpo. El timeout local aplica la contingencia exacta del contrato y conserva un origen distinto del 503 upstream. Las consultas carecen de refresh o replay automático.
- Broadcast `disponibilidad:<centroId>` / `actualizada` / `{centroId}` invalida el snapshot REST y vuelve a leer al reconectar. El GET y `expiraUtc` son las fuentes de estado. Prevé polling acotado si falla el canal.
